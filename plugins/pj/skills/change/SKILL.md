pj で作ったプロジェクトを「直したい」ときの**唯一の入口**。開発者は spec/design/build の層を知らなくていい。
自然文で言うだけで、pj が方向と正しいレイヤーを判定し、全部の整合を取る。

引数: $ARGUMENTS

## モデル起動時のゲート（`/pj:change` と打たれた起動では読み飛ばす）

ユーザーが明示的に `/pj:change ...` と入力したなら、この節は**丸ごと無視**する。**モデル（Claude）の判断で
起動したときだけ**通る。**`concepts.md` を読むのはゲート通過後。**

1. **pj 運用の repo か確かめる** — ルート `CLAUDE.md` に `<!-- pj:managed start` があるか grep する。
   **無ければ即座に降りる**（何も読まず書かず、「この repo は pj 運用ではないので通常どおり進めます」と一行）。
2. **必ず承認を取る** — change は `reconcile` も含めて**常に成果物を書き換える**（読み取り専用モードを持たない）。
   AskUserQuestion で「**対象 product** ／ **何を直すか**」を1文で確認する。**変更の高度（L0〜L4）と正レイヤーは
   ここで断定しない**——concepts を読んでから判定するので、承認文には書かない。
3. **承認が得られなければ何も書かずに降りる。** 代案を押し売りしない。

## 最初に必ず読む

- **`../../_shared/concepts.md`**（背骨）。**変更の高度 L0〜L4 の表は §16**、鎖と保守規律は §8。
- **UI に触れる変更と判定したら `../../_shared/visual.md`**（§V1 視覚の正 / §V2 intake）。
- **package の切り出し・境界に触れるなら `../../_shared/product-model.md`**。

**編集はこの skill が自分で行う。** 他 skill の「軽量修正モード」に委譲しない —— そのモードは
**ID を増減しないもの専用**で、増減するものを `/pj:change` に送り返す側だから（concepts §7 モード5）。
委譲すると送り返し合いになる。編集の作法（変更履歴・`updated`・readiness・影響1個提示）は
**concepts §8 の手順に従う**（作法を借りるのであって、モードを呼ぶのではない）。

## 手順

### 1. 意図と状況の把握

- `$ARGUMENTS`（自然文の変更要望）を読む。
- **未反映の変更**を確認する: `git status` / `git diff` で手編集済みの code がないか、`docs/` 各成果物の
  `updated` と実装の新しさにズレがないか（drift 兆候）を見る。
- **運用宣言を保証**: ルート `CLAUDE.md` に `<!-- pj:managed -->` ブロックが無ければ stamp する（concepts §17）。

### 2. 対象 product を特定する（層より先・concepts §2）

**層を決める前に「どの product の話か」を決める。** ここが決まらないと直す先のファイルが決まらない。

1. concepts §2 の3箇所を glob して product を列挙する。
2. 依頼文の対象・`git status` に出たパス・直近の文脈から対象を決める。曖昧なら一言だけ確認。
3. **複数 product にまたがるなら、それ自体を宣言する**（「これは workflow と app の両方に効きます」）。
   またがる変更は**上流の product から直す**（package → それを使う app の順。逆にすると app を2回直す）。

**「これは package に切り出すべき」と判断したときの扱い**:

- 既定は **L3**（HOW が変わる・WHAT は不変）。`/pj:setup package <name>` で器を作ってからコードを移し、
  app 側は **install して使う形**（workspace 依存）に直す。相対 import で参照させない。
- **切り出しで AC を増減させない。** 増減が要ると分かった時点で **L2 に上げ**、spec から直す。
- 切り出したら、その package が **app を知らない状態になっているか**を確認する（app の語彙・型が付いてきて
  いたら切り出せていない・product-model.md）。

### 3. 方向の自動判別

- **能動（トップダウン）**: 新しい振る舞い・技術・挙動への変更要望 → 正のレイヤーを**先に**直し、下へ伝播。
- **受動（ボトムアップ / reconcile）**: code/docs が**既にズレている**（手で code を直した・引数が `reconcile`・
  drift 検出）→ **まず `audit`**（drift-auditor・concepts §14）で鎖の切れ目を検出し、実態に合わせて docs を
  追従させる、または差分を提示して「どちらが正か」を決める。
- 判別がつかなければ**一言だけ確認**する。

### 4. 高度と正のレイヤーを特定して宣言

**高度 L0〜L4 の表は concepts §16。** 上から当てはめ、対応する正のレイヤーを決める:

- 振る舞い・仕様（WHAT）→ `docs/specs/` ／ 技術・構造（HOW）→ `docs/design/`
- **全 product 共通の作法** → **root の `docs/design/conventions.md`**（concepts §13）。「全 package で
  こうする」は package の design にも app の spec にも書かない
- 純粋なバグ／実装都合（挙動は仕様どおり）→ code / test のみ
- **取り込んだ出典の差し替えは既定 L3**（AC の増減を伴うと分かった時点で L2 に上げる）

特定したら**必ず一言宣言する**: 「これは〈product〉の〈振る舞い/技術/実装〉の変更なので **〈ファイル〉が正**。
そこを直して〈下流〉に伝播します」。これにより、層も product も知らない開発者が**使うたびに受動的にモデルを学ぶ**
（覚える義務はない）。

> **L0/L1 は即実行。L2〜L4 は「どの層をどう変え・どこまで伝播するか」を一行確認してから動く**
> （黙って深い手術をしない）。**迷ったら高度を1つ上げて確認する。**

### 5. 適用＋トレースの鎖の伝播

- **能動**: 正レイヤーを編集 → 受入条件が増減したら **AC を採番**（concepts §4）→ 対応する test を追加/更新
  （落ちる→緑）→ code を実装 → **影響 AC のテスト緑を確認**。
- **受動**: code の実態から対応する AC/spec を辿り、docs を追従させる（不足 AC を採番して追加、test を補完）。
  実態と仕様の**どちらが正か曖昧なら提示して確認**（勝手に上書きしない）。
- **UI に触れる変更**: `design-language.md`（visual.md §V1）を参照する。新しいデザイン原則が要るなら
  **DL-NN を採番**して追記し、`DL ↔ コンポーネント(@satisfies DL-NN) ↔ 使用箇所` の鎖を伝播する。
- **取り込んだ出典がある成果物**（`docs/design/intake/<intake-id>/`・visual.md §V2）:
  - **体験そのものを変えるなら、出典を先に更新してから実装に伝播**する（実装だけ変えると出典が嘘になる）。
    振り分けが増減したら `intake.md` の**振り分け表**を直し、AC / DL を追従させる。
  - **DS を当てると出典の意図が壊れた**という報告を受けたら、折衷せず **DL-NN を1本採番**して
    design-language と `intake.md` の「拾わなかったもの」に記録する。
  - **「実装を見たが気に入らない。作り直した」は `/pj:design intake <パス> <intake-id>`** に案内する
    （差し替えの安全確認は design 側が持つ）。そこから **AC の廃止が必要**と判定されて戻ってきたら、
    L2 としてここで spec から直す。
- **置き場が表に無いものを新設しない**（concepts §12）。表に無い種類のものが要ると分かったら、**それ自体が
  作法の変更**なので conventions を正として直してから実装に伝播する。
- **product 境界を壊さない**（concepts §2）。package を触るとき、app の型・語彙・ファイルを引き込んで
  辻褄を合わせない。必要なものは**注入**にする。境界を越えないと直せないなら、それは「切り出しが
  間違っていた」という上位の判定なので、**そう宣言してから**設計を見直す。
- どちらの方向でも、触れた各レイヤーで **変更履歴・`updated`・その product の2軸ダッシュボードを同期**
  （concepts §8・§9）。**package を触ったら root の product 表も引き直す。** 前提が覆ったら readiness を**下げる**。

### 6. 報告

- 触れたファイルを **product × 層横断で1リスト**にして提示（どの product の spec/design/test/code か）。
- **完了基準は build と同じ**——触れた feature の**全受入条件テストが緑**。最後に **grep で「全 AC に
  テストあり」を機械検証**する（concepts §4）。
- 残った未決や readiness 後退があれば明示。大きい変更で関連 feature に波及しそうなら**1個だけ**提示する。

## 採番の実務（規約の正は concepts §4）

- **`(<feature>-AC-NN)` の増減は `/pj:change` が唯一の採番者**（新規の書き起こしだけ `/pj:spec`）。
- **`(DL-NN)` は `/pj:design` と共同**（design の対話・`intake` モードでも採番される）。

いずれも他 skill の**軽量修正モードでは増減しない**。形式・不変ルール・欠番の扱いは §4。ここでは書き方だけ:

- 受入条件: `- [ ] (<feature>-AC-NN) <検証可能な条件>` → test 名かコメントに同じ ID を含める
  （例: `test('event-AC-12 予算未入力で保存できない', ...)`）
- デザイン原則: `- **(DL-NN) <原則>** — <検証可能な内容>` → コンポーネント先頭に `@satisfies DL-NN`
- 採番したら各文書末尾の**採番台帳の次番を進める**。

## やってはいけないこと

concepts §15（全レイヤー共通）に従う。`/pj:change` 固有で特に外せないのは2つ:

- **受動時、実態と仕様が食い違うのに確認せずどちらかを上書きする**（どちらが正かはユーザーが決める）。
- **誤ったレイヤーで辻褄を合わせる**——振る舞い/設計の変更を code だけにパッチしない（＝ドリフトを作らない）。
  **product 境界を越えて辻褄を合わせるのも同じ**（境界は仕様であって都合ではない・concepts §2）。
