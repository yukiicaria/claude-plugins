# pj — product モデルの実務（分割の基準・可搬・強制）

> `concepts.md` §2 が **product の定義**（単位・発見・依存と準拠・独立の2判定）を持つ。
> このファイルは**その実務**——「いくつに割るか」「可搬をどう満たすか」「どう強制するか」。
>
> **読むスキル**: `/pj:setup`（`package` / `stack` / `sync`）／`/pj:change`（切り出しの判定）／
> `/pj:build`（package を実装するとき）／`agents/drift-auditor`（監査）。
> **package を扱わないターンでは読まなくてよい。**

## §P1. いくつに割るか — 層の名前を先に決めない

**「コアと UI の2つ」のような固定の型を持たない。** 割る数は責務の数ではなく、**下の基準に当てはまった数**で
決まる。当てはまらないなら1つのままでよい。

> **迷ったら割らない。** 1 package の中を `src/<関心>/` に分け、**lint で依存方向を強制**すれば、境界は
> package を増やさなくても敷ける（Nx の module boundaries と同じ考え方）。**後から割るのは簡単だが、
> むやみに増やした package を統合するほうが高くつく。**

**割る根拠になるもの**（1つでも当てはまれば割る）:

```
依存の重さが違う      FW・DS に依存する部分としない部分。最も確実な根拠。
                      コアがバッチ・CLI から使えなくなるのを防ぐ
                      （実例: TanStack Query は query-core に react を入れず、
                        react-query 側の peerDependencies にだけ置く）

第三者が実装を書く    利用者が自分の実装（プロバイダ・アダプタ）を足す想定なら、
                      **契約（型とインターフェース）をコア本体から分ける**
                      （実例: AI SDK のプロバイダは @ai-sdk/provider だけに依存し、
                        コア本体 ai には依存しない）

利用者が選んで入れる  複数の実装が入れ替え可能で、使うものだけ入れたい
                      （Slack だけ使う人に他社の SDK を持たせない）

テストが遅い          CI を占有し、変更が一部しか触らない

オーナーが違う        別のチームが触る。境界とレビュー割当が曖昧になる
```

**割る根拠にならないもの**:

- **「層だから」** — 層は依存の方向の話であって、パッケージの数の話ではない。方向は lint で守れる
- **「型だけだから軽い / 重い」** — 型は実行時に消えるが、それは分割の理由にも、しない理由にもならない
- **常に一緒に変わるもの** — 境界のコストだけかかって利得がない

**構造の作法**:

- **公開名とディレクトリ名は一致しなくてよい。** 並びやすいディレクトリ名と読みやすい公開名は別の都合で決まる
- **パッケージを増やさずに関心を分ける手段としてサブパス export がある**（`<pkg>/events` のように
  1 package の中で入口だけ分ける）。版を分ける必要が無いならこちらで足りる
- ディレクトリの深さと配置は concepts §2「product の発見」が正

## §P2. 可搬 — 機械で測れるほう

**最初から満たす。「切り出すときにやる」ことではない。** workspace の hoisting が不足を隠すので、
**壊れていても静かに壊れる**——実際に切り出すまで誰も気づかない。後から剥がすのは、root に寄せた設定を
1つずつ引き剥がす作業になる。

```
tsconfig     親を extends しない。または extends 先が消えても壊れない
             （app の FW プラグイン・paths・jsx 設定を継承しない）
依存         import する外部パッケージが全て package.json に宣言されている
             テストランナー・型定義（vitest, @types/node 等）も devDependencies に書く
テスト       自分の設定だけで走る。setup ファイルが app を指していない
script       type-check と test の両方がある（片方欠けると CI が素通りする）
peer         FW・DS ライブラリ（react, DS）は peerDependencies。利用側と二重に入れない
scope        実装が scope 名（`@<scope>/`）を前提にしていない
公開 API     `src/index.ts` に閉じる。他 package の内部を直接 import しない
```

- **完成条件は `bun run type-check` と `bun run test` が package 単体で通ること。**
  root から一括で走らせて通るのは、可搬の証明にならない。
- **判定は自動化できる。** 対象 package を空ディレクトリにコピーし、`bun install` して上の2コマンドを走らせる。

## §P3. 強制（4枚）

1. `packages/<name>/package.json` の dependencies に **app を書かない** → import した時点でビルドが落ちる
2. import の方向を **lint** で塞ぐ（相対パスでの脱出を防ぐ）:

   ```js
   // packages/ から app（src/）への参照を禁止する
   'import/no-restricted-paths': ['error', {
     zones: [{ target: './packages', from: './src',
               message: 'package は app を知らない（pj concepts §2）' }],
   }]
   ```

3. **audit（drift-auditor）が docs レベルの違反を見る**（package spec からの app 参照・app 固有語彙の混入）
4. **可搬を実際に試す**（§P2）。1〜3 は「app を知らない」を守るが、**可搬はそれとは別の境界**で、
   1〜3 を全部通っても落ちる（実例: 依存グラフは完璧なのに vitest を1つも宣言せず root の設定を借りていた）

## §P4. アダプタは分類ではなく、判定にかける

**「アダプタだから まとめる」ではない**（concepts §12 の3分類）。同じ判定（テストできるか）を当てる。

```
まとめる   インターフェースを既存の実装に繋ぐだけのもの。
           落ちるところが無く、テストに書くことが無い

挙動       外界の癖を吸収するもの。AC を持ち、テストが書ける。
           例: 再送の条件、レート制限、上限（「N 日先まで」）、受信の検証、
               失敗の分類（再送してよい失敗か・諦める失敗か）、表現の変換
```

- **外部サービスに繋ぐアダプタは、たいてい「挙動」になる。** 相手の仕様に合わせた判断がそこに入るため。
  「繋ぐだけ」に見えても、**落ちたときにどうするかを決めているなら挙動**。
- product として切り出したアダプタが「まとめる」だと、**AC を持てない product** という矛盾になる。
  その場合は分類を疑う前に**「本当に product にする必要があるか」を疑う**（§P1）。
- 良い設計は自然にこの形になる。例: `src/core/`（挙動）／ `src/parts/`（見た目）／ 組み立て役の1ファイル（まとめる）。
