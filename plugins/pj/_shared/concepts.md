# pj パイプライン — 共通の背骨（concepts）

> このファイルは `/pj:setup` `/pj:spec` `/pj:design` `/pj:build` `/pj:change` の **5スキル共通の唯一の出典**。
> 各スキルは起動時にまずこれを読み、ここで定義する軸・モード・規律に従う。
> 各スキル固有の振る舞い（何を生成するか・どんな質問をするか）だけが各 SKILL.md にある。
> `/pj:setup` は最上流の **Day 0（立ち上げ）**。spec/design/build の手前で、足回りと器（pj-managed な
> CLAUDE.md・デザインシステム）を用意する。中身（docs/ 本体）は作らず spec/design の init に引き渡す。

> **言語: pj スキル実行中のユーザーへの応答は必ず日本語で書く**（成果物の md・コード内コメントも日本語を既定とする）。
> ユーザーが他言語を明示した場合のみそれに従う。

## 0. pj とは

spec → design → build の3フェーズで **1つのプロジェクトを WHAT から コード まで一貫して育てる**
仕様駆動パイプライン。3フェーズは別々のツールではなく、**同じ真実を、同じ語彙・同じ評価軸・
同じ盤面・同じ保守規律で育てる一体のファミリー**。

## 1. 1つの真実の3レイヤー（トレース可能）

`docs/` がプロジェクトの単一の真実。3レイヤーに分かれ、**下は上から導出され、必ず上へ辿れる**。

| レイヤー | 問い | スキル | 成果物 |
|---|---|---|---|
| **spec**   | 何を・どう振る舞うか | `/pj:spec`   | `docs/specs/`（overview / features / glossary） |
| **design** | どの技術で・どんな構造で | `/pj:design` | `docs/design/`（stack / data-model / conventions / adr ／ UI があれば design-language・mocks） |
| **build**  | 実際に作る（テスト先行） | `/pj:build`  | `src/` + テスト（状態は overview ダッシュボードに反映） |

**トレースの鎖（保守の基盤）**:
- `受入条件（spec） ↔ test ↔ code` — 受入条件が変われば test を直し、test が変われば code を直す
- `design 決定 ↔ コードモジュール / スキーマ` — design が変われば該当 code を直す
- `DL-NN ↔ コンポーネント`（視覚・横断／visual.md §V1）・`UX-NN ↔ 実装`（体験・画面固有／visual.md §V2）
- 各成果物は `[[リンク]]` と file:line で互いを指す。鎖が切れた状態を「ドリフト」と呼ぶ（§4）
- 鎖は**安定 ID** で機械検証可能にする。ID の形式・採番者・不変ルールは **§1.1 が唯一の定義**。

## 1.1 安定 ID 規約（唯一の定義 — 他所はここを参照する）

鎖を「意味解釈なしに grep で機械検証」できる状態に保つための規約。肥大化してもドリフト検出が安く済む。
**pj 内の他のどの文書も、ID の規則をここ以外に書かない**（重複させるとそこがドリフトする）。

| ID | 何に振るか | 置き場 | 参照する側 | 採番者 |
|---|---|---|---|---|
| `(<feature>-AC-NN)` | 受入条件 | `docs/specs/features/<feature>.md` | test 名 / コメント | **`/pj:change`** |
| `(DL-NN)` | デザイン原則・トークン・コンポーネント語彙（**横断**） | `docs/design/design-language.md` | コンポーネント先頭の `@satisfies DL-NN` | **`/pj:design`・`/pj:change`** |
| `(<mock>-UX-NN)` | モックの**挙動**のうち静的に見比べても検出できないもの（**画面固有**・visual.md §V2） | `docs/design/mocks/<mock>/mock.md` | 実装コードの `@satisfies <mock>-UX-NN` | **`/pj:design`・`/pj:change`** |

**全 ID 共通の不変ルール**:
- **一度振った ID は変えない。** 廃止したら**欠番**にし、**再利用しない**（欠番はその旨を明記する）。
- **NN は2桁ゼロ埋めの連番**。次番は既存の最大値 +1（`design-language.md` は末尾に**採番台帳**を持つ）。
  **欠番にした ID は文書内に「欠番」として明記**し、なぜ廃止したかを1行残す。
- **採番は上表の採番者だけが行う。** 他の skill の軽量修正モードで ID を増減しない（§3 モード5）。
  ID の無い受入条件・原則が生まれた時点で鎖が切れる。
- 鎖の検証は**どの ID も同じ形**: 「全 ID に参照側が存在するか」を grep で突合する（未参照 = 未実装）。
- **ID を1つ増やしたら、この表に1行足すだけで済むようにする。** 他所は種類を列挙せず「§1.1 の安定 ID」と書く
  （列挙すると、増えたときにそこが漏れる）。

## 2. readiness 軸（0〜5）— 全レイヤー共通

**唯一の評価基準**: 「**この成果物を次フェーズにそのまま渡したら、追加対話なしに進めるか**」。
項目数や文章量では測らない。**残っている意思決定の量**で測る。レイヤーごとの具体化:

| レイヤー | readiness が測るもの | 単位 | 格納先（frontmatter） |
|---|---|---|---|
| spec | 実装/設計 Agent が**追加の設計対話なし**に着手できるか | feature | `docs/specs/features/<name>.md` の `progress` |
| design | 実装 Agent が**追加の技術判断なし**にコードを書けるか。**UI があれば「追加の視覚判断なし」に画面を組めるかも含む**（design-language が揃い、モックのある画面はモックと UX-NN が揃っているか） | 成果物ごと | `stack.md` / `data-model.md` / `conventions.md` /（UI があれば）`design-language.md` の `progress` |
| build | その feature の**全受入条件のテストが緑**か | feature | `docs/specs/features/<name>.md` の `build_progress` |

- **readiness は必ず frontmatter に保存する。** 表示のたびに推定し直すと値が揺れて、下がったことに
  気づけなくなる（§2 の「毎回つけ直す」は**保存値を更新する**という意味であって、都度の再推定ではない）。
- **design 全体の確定度 = 上表の各ファイルの `progress` の平均**（UI が無ければ design-language を除く）。

| 値 | バー | 意味 |
|---|---|---|
| 0 | □□□□□ | 何もない（ファイルだけ） |
| 1 | ■□□□□ | 概要だけ |
| 2 | ■■□□□ | 主要な方向性が見えてきた |
| 3 | ■■■□□ | 主要フロー・構造は固まった。各部の中身／エッジは未定（＝まだ対話が要る） |
| 4 | ■■■■□ | 細部・エラーケースまで概ね詰まり、対話はほぼ不要 |
| 5 | ■■■■■ | 追加対話ゼロで次フェーズにそのまま渡せる |

**運用ルール（全レイヤー厳守）**:
- **4-5 をつけてよいのは「追加対話が不要」と言い切れるときだけ。** これから「詰める／深掘りする」と
  話している成果物は最大 3。
- **枠・構造が決まっただけでは 3 どまり。** 中身が薄いのに 4-5 にしない。
- readiness は**ラチェットではない。毎回つけ直す。** 論点が増えた・前提が覆った・新たな未決が出たら、
  見栄えのために高い値を維持せず**遠慮なく下げる**。後退は変更履歴に残す。
- バー表記（■と□）を正とする。数値は補助。

## 3. 共通モード（全スキル同じ意味）

引数と文脈から **1つの振る舞いを選ぶ**。判断順は上から:

1. **status** — 「今どんな感じ?」「進捗」系、または `status` で始まる → 盤面表示（**編集しない**）
2. **next** — 「次どこ?」「何から?」系、または `next` → 次の一手提案（**編集しない**）
3. **review** — 「これでいい?」「見て」「レビュー」系、または `review` → sub-agent 委譲で客観判定（**編集しない**、§7）
4. **audit** — 「ズレてない?」「乖離」「同期できてる?」系、または `audit` → ドリフト監査（**編集しない**、§4・§7）
5. **軽量修正** — 既存成果物への一点修正依頼のうち、**§1.1 の安定 ID を増減しないもの** →
   即時反映（サマリ省略、§4）。**ID の増減を伴うものはこのモードで処理せず `/pj:change` に送る**
   （ここを緩めると ID の無い受入条件・原則が生まれ、§1.1 の鎖が機械検証できなくなる）。
   **ID の種類をここで列挙しない**（増えたときに漏れる。正は §1.1 の表）
6. **対話（既定）** — 上のどれでもない → サマリ → 会話で詰める

> 次フェーズへは**専用の受け渡し成果物（handoff）を作らない**。各 skill（特に build）は spec/design を直読みする。
> 既存物の修正は層を意識せず **`/pj:change`**（§9）に投げてよい。

各モードのレイヤー別の具体（status が何を出すか等）は各 SKILL.md が定義する。共通の作法:
- status/next/review/audit は**読むだけ。成果物を編集しない**
- 編集する系（対話・軽量修正・`/pj:change` の反映）は**毎ターン応答前に関連ファイルを読み直す**
  （ユーザーがエディタで直接編集していることがある）
- 編集 **diff は見せない**。「○○.md を更新しました（要点1行）」程度に留める
- 気付いた論点は溜めず**その場で 1〜2 個ずつ**出す。終わり際にまとめて出さない

## 4. メンテナンス規律（パイプラインの第一級市民）

一度作って直す、を最初から組み込む。原則: **変更は正しいレイヤーから入れ、トレースの鎖を下へ伝播させる。**

**開発者の入口は `/pj:change` 一本**（能動「○○を変えたい」／受動「もう code を直した・ズレてる」を
自動判別。層を知らなくていい）。`/pj:change` が方向と正レイヤーを判定し、以下の規律を**開発者に代わって
実行する**。開発者が覚えるのは「直したい → `/pj:change`」だけ。以下はその下で働く仕組み。

**典型シナリオ**:
1. **実装中に仕様の誤りに気づく** → build で勝手に辻褄を合わせず、**`/pj:change <気づいたこと>`** に投げる
   （L2 と判定され spec が正レイヤーになる）→ 受入条件が変われば AC を採番し test→code を辿って直す。
2. **仕様変更要求** → spec→design→build を**増分**で流す。greenfield ではなく差分として扱う。
3. **定期 or 不安なとき** → `audit` モードで **drift-auditor**（§7）が
   `code ↔ 受入条件 ↔ design` の食い違いを検出・報告する。

**軽量修正モードの手順（全レイヤー共通）**:
0. **スコープ判定**: その修正が **§1.1 の安定 ID**（受入条件・デザイン原則・モックの挙動 …）を
   **増やす/廃止する**なら、ここで処理せず「これは ID の増減を伴うので `/pj:change` で入れます」と
   告げて `/pj:change` に渡す（§3 モード5）。
1. 該当ファイルを特定（不明なら一言で確認）
2. 該当箇所を更新
3. そのファイル末尾の `## 変更履歴` に `YYYY-MM-DD: <変更内容>` を追記
4. frontmatter の `updated` を**今日の日付**に更新
5. 影響しそうな**下位レイヤー / 関連成果物を 1 個だけ**提示（push しすぎない）
6. 変更で論点が再び開いたら readiness を**下げる**（§2）

**不変条件**: すべての成果物は `updated` と `## 変更履歴` を持つ。前提を覆して書き直したら
「○○の前提を破棄し△△に作り直し」と履歴に残し、古い前提を参照していた**他の記述も追って直す**
（作り直しの残骸を残さない）。

## 5. ダッシュボード（2軸）

`docs/specs/overview.md` の進捗ダッシュボードは **feature × 2軸**（spec readiness と build readiness）。

| 機能 | spec | build | 残課題 |
|---|---|---|---|
| contacts | ■■■■□ | ■■□□□ | 名寄せ候補の粒度 / 実装中 |
| event | ■■■■□ | □□□□□ | 未着手 |

- **spec 軸**は `/pj:spec` が、**build 軸**は `/pj:build` が更新する（design の確定度は `docs/design/` 側で持つ）。
- feature を更新するたびに同期。全体進捗は各軸の平均をバー表記。
- build readiness 5 = その feature の全受入条件テストが緑。
- **進捗の正はこのダッシュボード1箇所**。overview の「コア機能」は何があるかだけを持ち、完了状態
  （チェックボックス等）は**持たない**。同じ事実を2箇所に持つと必ずズレるため。

## 6. glossary — 全レイヤー共通の用語辞書

`docs/specs/glossary.md` がプロジェクト全体の**用語の正**。spec の本文だけでなく、**design の
スキーマ名・コードの識別子も同じ語に従う**。曖昧/衝突/恣意的な名前は **terminologist**（§7）で
横断監査し、canonical 用語に寄せる。用語の一意性は実装の誤りを防ぐ最重要要素。

## 6.5 視覚と体験の正 → `visual.md`（UI を持つプロジェクトのみ）

UI の正は本ファイルではなく **`_shared/visual.md`** が持つ（このファイルは全 skill 共通の背骨に徹する）:

| 節 | 内容 |
|---|---|
| **`visual.md` §V1** | **design-language** — 全画面共通の視覚の正（DL-NN）＋ デザインシステムの3スロット契約 |
| **`visual.md` §V2** | **モック** — こだわりの強い画面の体験の正（UX-NN）。忠実再現の運用・置き場・採番の絞り方 |

- **読むのは UI に触れる skill だけ**: `/pj:setup`（DS 導入）・`/pj:design`・`/pj:build`（UI 実装時）・
  `/pj:change`（UI に触れる変更時）。**`/pj:spec` は読まない**（WHAT に視覚は含まれない）。
- **CLI 等 UI の無いプロジェクトでは誰も読まない。**
- ID 規約（DL-NN / UX-NN）の正は本ファイルの **§1.1**（visual.md 側には書かない）。

## 7. sub-agent 委譲（トークン重い読み込みはメインを汚さない）

| agent | 役割 | 呼ばれるモード |
|---|---|---|
| `pj:readiness-reviewer` | 「次フェーズが追加対話なしに進める水準か」を批判的に判定（spec/design 両対応） | review |
| `pj:terminologist` | 用語・命名の一貫性を全レイヤーで監査し canonical 案を返す | spec の用語整理 / audit |
| `pj:drift-auditor` | 鎖（受入条件 ↔ test ↔ code / design ↔ 実装 / DL-NN・UX-NN ↔ 実装）の切れ目を検出 | audit |
| `pj:design-reviewer` | UI が design-language（視覚の正・visual.md §V1）とモック（体験の正・visual.md §V2）に従うかを DL-NN / UX-NN・file:line つきで監査 | review / audit（UI 対象時） |

委譲の作法: sub-agent を起動し、**対象（docs パス / 特定 feature）とレイヤー**を渡す。返ってきた結果は
**丸投げせず要点を整理**してユーザーに伝える（重大な指摘を先頭に）。review/audit 自体では**編集しない**。
build の review は専用 agent でなく既存の `/code-review` `/security-review` `/verify` に委譲してよい。

### audit の起動仕様（全 skill 共通・ここが唯一の定義）

ドリフトは**レイヤーをまたいで**起きるので、audit は**レイヤーごとに分けない**。`/pj:spec audit`
`/pj:design audit` `/pj:build audit` `/pj:change`（受動）は**どれも同じ監査**を起動する:

- agent: **`pj:drift-auditor`**
- 対象: **`docs/specs/` ＋ `docs/design/` ＋ `src/`**（呼び出し元の層に関わらず常に3点セット。
  spec だけ・design だけを渡すと、鎖の切れ目が対象外に落ちて検出漏れになる）
- 観点: **§1.1 の全 ID の鎖**（`受入条件 ↔ test ↔ code` / `DL-NN ↔ コンポーネント` /
  `UX-NN ↔ 実装`）＋ `design 決定 ↔ 実装・スキーマ`。**ID が増えたら鎖も増える**（列挙を正にしない）
- UI の視覚違反・**モックとの構成の乖離**を深掘りするときのみ **`pj:design-reviewer`** を併用する
- 特定 feature に絞りたいときは対象は3点セットのまま、**スコープとして feature 名を渡す**
- 結果は要点整理して報告し、**編集しない**（直すのは `/pj:change`）

## 8. やってはいけないこと（全レイヤー共通）

- 決まったテンプレ質問を機械的に上から順に投げる（文脈に応じて必要な質問だけ出す）
- ユーザーが「保留」と言った論点を蒸し返す（`open_questions` に積んで先に進む）
- 編集 diff を毎回見せる
- 気付いた論点を溜め、終わり際にまとめて出す
- status / next / review / audit モードで成果物を編集する（読むだけ）
- レイヤーをまたいで辻褄合わせをする（誤りは正しいレイヤーに戻して直す。§4）
- 過去に決めた前提に固執し、覆すべき場面で小さな差分修正に逃げる（作り直しをためらわない）
- 見栄えのために readiness を高いまま維持する（実態に合わせて下げる）

## 9. 変更の高度トリアージ（`/pj:change` の中身）

`/pj:change <やりたいこと>` は開発者の日常入口（§4）。依頼と現在の docs/code/test を読み、**変更の「高度」を
判定して正しいレイヤーから直し、トレースの鎖を下流まで伝播させる**。開発者は層を意識しない。

**判定（上から当てはめ、一行で宣言してから動く）**:

| 高度 | 何が変わるか | 例 | 入口レイヤー / 伝播 | docs |
|---|---|---|---|---|
| **L0** 局所/コスメ | 振る舞いも設計も不変（spec が規定していない範囲） | ボタンの色・余白・文言・無害なリファクタ | code 直接 → test 緑 | 触らない |
| **L1** 実装バグ | 受入条件は正・code が違う | 仕様どおり動いていない | build: test↔code を辿って修正 | 触らない |
| **L2** 振る舞い変更 | WHAT が変わる | ルール追加・項目追加・フロー変更 | **spec → design 影響確認 → build** | specs（＋設計波及あれば design） |
| **L3** 技術/構造変更 | WHAT 不変・HOW が変わる | 実装方式・スキーマ・ライブラリ変更 | **design → build** | design |
| **L4** 根本 | spec も design も | コンセプト転換 | **spec → design → build を増分で** | 両方 |

> **モックの差し替え（リモック）は既定 L3**（体験＝HOW が変わる・WHAT は不変）。実装を見て気に入らず
> モックを作り直したときは `/pj:design mock` が扱う。**AC の増減を伴うと分かった時点で L2 に上げ**、
> spec から直す（visual.md §V2 / `/pj:design mock` の「差し替え」）。

> **L0 コスメであっても design-language（DL-NN・visual.md §V1）に準拠する**。色・余白・文言・コンポーネント選択も視覚の正の範囲内で。

**secured 担保（誤った高度での処理を防ぐ）**:
- **L0/L1 は即実行**。**L2〜L4 は「どの層をどう変え・どこまで伝播するか」を一行確認してから**動く（黙って深い手術をしない）。
- **誤レイヤーでの辻褄合わせを禁止**（§8）。振る舞い/設計の変更を code だけにパッチしない＝ドリフトを作らない。
  必ず正レイヤーに上げ、`受入条件 ↔ test ↔ code` / `design ↔ code` の鎖を辿って下流まで反映する。
- **受入条件の増減には安定 ID を自動採番**（規約は §1.1。**AC-NN は `/pj:change` が唯一の採番者**）。対応する
  test を同じ ID で追従させ、最後に grep で「全 AC にテストあり」を機械検証する。
- **受動の入口も同じ**: 「もう code を直した」「ズレてる気がする」は、まず `audit`（drift-auditor §7）で
  鎖の切れ目を検出 → 切れていれば正レイヤーに反映して埋める（code だけ進んで docs が遅れた状態を解消）。
- 完了基準は build と同じ（触れた feature の**全受入条件テストが緑**）。触れた docs は `updated` と変更履歴を同期（§4）。

迷ったら高度を1つ上げて確認する（浅く済ませて取りこぼすより、正レイヤーに上げる方が安全）。

## 10. プロジェクトへの運用宣言（managed block）

pj で運用するプロジェクトは、**ルート `CLAUDE.md`（毎セッション常時ロード）に「このプロジェクトは pj で回す」運用宣言を
持つ**。`concepts.md` 等のプラグイン内部文書は skill 実行中しか読まれないため、宣言が無いと**普通のセッションや
新しい人が入口（`/pj:change`）に辿り着けない**。そこで宣言を**プラグインが所有・生成する管理ブロック**として焼き込む
（防御: ルールが向こうから来る）。

**正準の管理ブロック**（マーカーで挟む。ブロック内は pj が生成し、人は手編集しない。マーカー外は保全）:

```markdown
<!-- pj:managed start — pj パイプラインが生成・更新する。ブロック内は手で書き換えない -->
## 運用モデル（pj パイプライン）

このプロジェクトは pj パイプラインで運用する。真実は docs/ の3層（下は上から導出、必ず上へ辿れる）:
- 振る舞い(WHAT) → `docs/specs/` ／ 技術・構造(HOW) → `docs/design/` ／ 実装(テスト先行) → `src/` ＋ tests

- **直したい・変えたいときの入口は `/pj:change <やりたいこと>` 一本**（層は意識しなくてよい）。自然文で言えば
  変更の高度(L0コスメ〜L4根本)と正レイヤーを自動判定し、正しい層から直して下流（受入条件 ↔ test ↔ code）へ伝播する。
- 状況確認は `/pj:spec status`・`next`、客観チェックは `review`・`audit`。仕様=`/pj:spec`／設計=`/pj:design`／実装=`/pj:build`。
- 受入条件には安定 ID `(<feature>-AC-NN)` を振り、test がそれを参照する（鎖を grep で機械検証）。
<!-- pj:managed end -->
```

**stamp 規律（冪等・全 skill 共通）**:
- **編集系フロー**（spec の init / 対話・軽量修正、`/pj:change` の反映）に入ったら、ルート `CLAUDE.md` に
  `<!-- pj:managed start -->`〜`end` が**無ければ上記ブロックを stamp**（挿入）する。基本は末尾近く or Overview 直後。
- 既にマーカーがあれば**重複させない**。pj 側が進化して正準ブロックが更新されたら、**マーカー区間だけ差し替え**
  （マーカー外の手書きルールは触らない）。
- **read-only モード（status / next / review / audit）では stamp しない**（書かないのが原則・§3）。
- プロジェクト固有の運用注記を足したいときは**マーカー外**に書く（次回の再生成で消えない）。
