# pj — 視覚と体験の正（UI を持つプロジェクトのみ）

> `concepts.md` が **5スキル共通の背骨**であるのに対し、このファイルは **UI を持つプロジェクトだけ**の出典。
> **CLI 等 UI の無いプロジェクトでは誰も読まない**（design-language を N/A 宣言して終わり）。
>
> **読むスキル**: `/pj:setup`（DS 導入 = §V1 の3スロット契約）／`/pj:design`／`/pj:build`（UI 実装時）／
> `/pj:change`（UI に触れる変更時）。**`/pj:spec` は読まない**（WHAT に視覚は含まれない）。
>
> ID 規約（`DL-NN` / `UX-NN` の形式・採番者・不変ルール）の正は **`concepts.md` §1.1**。ここには書かない。

## §V1. design-language — 全画面共通の視覚の正

glossary が**用語の正**であるのと対称に、`docs/design/design-language.md` が**視覚の正**。spec から導出し
（design フェーズ）、全画面・全コンポーネントが従う。整合は **design-reviewer**（concepts §7）で監査する。
UI を持たないプロジェクト（CLI 等）では N/A 宣言で省略してよい。

**デザインシステムの 3スロット契約（DS 非依存）**: 視覚の共通化は特定 DS に依存しない3スロットで担保する。
`/pj:setup` がこれを各 DS（または preset）に当てはめて配線する:
- **実体** … 部品とトークンの本体（DS パッケージを install／preset は最小トークンを scaffold）
- **導線** … `src/components/CLAUDE.md` に DS の AI ドキュメント（llms.txt 等）を指すポインタ。UI 作業時に
  **自動ロード**され「ルールが向こうから来る」を成立させる（Claude が勝手にアイコン・色を発明しない導線）
- **正の宣言** … design-language §F に「**語彙・トークンの正 = <DS>**」を固定。DS があれば DL-NN はその差分だけ、
  preset は DL-NN が全部を担う。**プリミティブ族（アイコン筆頭・色・日付/数値書式 等）は単一窓口**を決め再発明させない

> 当面、生 color / 生 svg / 別ライブラリの **lint ブロック強制は入れない**（README の「まず warning、ブロックは
> 規律が固まってから」方針）。導線（上記）＋ audit の `pj:design-reviewer`（concepts §7）で運用する。

## §V2. モック — こだわりの強い画面の「体験の正」

design-language（§V1）は**全画面横断**の原則を持つ。しかし「ボタンをどこに置くか」「どの列を固定するか」
「ピンチでどう拡大するか」は**その画面固有**で、一行原則に圧縮すると必ず失われる。そこを担うのがモック。

### 運用は2行

> 1. **モックがある画面は、モックを忠実に再現する。**
> 2. **プロジェクトにデザインシステムが設定されていれば、語彙とトークンをそれに当てる。**

DS が無い（preset）プロジェクトなら 1 だけ。**既定は「全部再現」**であり、実装者が「どこがこだわりか」を
察して拾い上げる作業は無い（拾い漏れがそのままストレスになるため、判断を挟ませない）。

**衝突したときの規律**: DS を当てるとモックの意図が壊れる場合（部品の既定寸法が密度を壊す・相当部品が DS に無い等）、
**黙って妥協しない**。DS の語彙は使う（部品を再発明しない = DL-01）うえで、**`DL-NN` を1本足して差分を記録**する。
記録せずに折衷すると、モックとも DS とも違う第三の状態が生まれ、次に触る人が根拠を辿れない（concepts §8 の
「誤レイヤーでの辻褄合わせ」と同じ失敗）。

### いつ作るか（乱用防止）

全画面に作ると破綻する。**作るのはこだわりの強い画面だけ**:
- ✅ spec が「この画面が最も作り込む」と宣言している
- ✅ 一覧 × 時系列 × 直接操作のように、**テキストに落とすと必ず失われる**インタラクションがある
- ❌ CRUD フォーム・設定画面 → design-language（DL-NN）だけで足りる。モックを作らない

### 置き場と構成

```
docs/design/mocks/
  README.md                # 索引: どの画面にモックがあるか（1画面1行）
  <mock-id>/               # 1モック1ディレクトリ。<mock-id> は kebab-case
    mock.md                # このモックの正（出典・UX-NN 台帳・DS 衝突で足した DL）
    index.html             # 開いてそのまま動く実体
    <その他>               # 分割が必要なときだけ増やす
```

- **`<mock-id>` は原則 feature 名**（例: `grant-rounds`）。1 feature に複数画面あるときだけ
  `<feature>-<screen>` にする。
- **実体はリポジトリに置く**（URL 参照だけにしない）。忠実に再現する以上、正確な列幅・閾値・算出式を
  読める必要があり、URL は安定して読めないため。
- **ただし埋め込みアセットは剥がす。目安 100KB / モック。** フォント・画像・DS バンドルは参照に留める
  （実測: 埋め込み込みで 7.9MB のモックが、剥がすと 30KB になる）。
- **原典（生成元の artifact URL 等）は `mock.md` に必ず残す**（再生成・比較のため）。

### UX-NN を振る対象（絞る）

「忠実再現が既定」なら、**配置・列順・密度に ID は要らない**。モック実体と実装を見比べれば分かるので、
`design-reviewer`（concepts §7）の突き合わせで足りる。**ID を振るのは、静的に見比べても検出できない挙動だけ**:

- ジェスチャ（ピンチ / ⌘+wheel / shift+wheel / ドラッグ）
- 段階的開示の閾値（「列幅 34px 以上で数値が現れる」等）
- 複数スクロール面・固定列の同期
- オーバーレイの位置決め（上下反転・ビューポートのクランプ）
- 状態の保存（ズームのアンカー保持・入力の永続）

これらは**実装から抜け落ちても並べて見た限りでは気づけず**、ユーザーが操作して初めて分かる。だから
`@satisfies <mock>-UX-NN` で grep 検証可能にする（ID 規約は concepts §1.1）。1画面あたり数本に収まるのが健全。

### 差し替え（リモック） — 実装を見て気に入らず、モックを作り直したとき

実装を確認して「これは違う」となり、**新しいモックを作り直して当て直す**のは正常な経路。ただし
**既に AC・テスト・UX-NN・実装がある状態への上書き**なので、新規取り込みとは手順が違う（実務手順は
`/pj:design mock` の「差し替え」）。

**高度は既定 L3**（HOW が変わる・WHAT は不変。concepts §9）。振る舞いに触れるなら L2 に上げる。

**最大の落とし穴: モックに無いものを「削除」と読まない。**
モックは**ハッピーパスのダミーデータ**で作る。**エラー状態・空状態・権限による非表示・バリデーション・
確認ダイアログ**は描かれないのが普通。新モックに描かれていないことは「**否定**」ではなく「**未描画**」が既定。
ここを取り違えると、受入条件が静かに実装から消える（最も起きやすい事故）。

新モックの差分は3つに仕分ける:

| 種別 | 例 | 行き先 |
|---|---|---|
| 構成・見た目 | 列順・余白・ボタン位置・密度 | **そのまま再現**。ID は振らない |
| 挙動 | ズームをやめてページャにする | **UX-NN を採番／欠番化** |
| **振る舞い（WHAT）** | 合計行が消えた・入力項目が減った | **ここで処理しない。`/pj:change`（L2）で spec から直す** |

- **旧モックは git 履歴に残る**ので `index.html` は上書きしてよい。ただし `mock.md` の「出典」は
  **世代を積む**（いつ・どの原典から差し替えたかを消さない。後から「なぜ変えたか」を辿るため）。
- **UX-NN は作り直しても振り直さない。** 残る挙動は**同じ ID を維持**、消えた挙動は**欠番**、
  増えた挙動は**新番**（concepts §1.1 の不変ルール）。モックを作り直すたびに 01 から振り直すと鎖が切れる。
- **部分だけ作り直した**場合は `index.html` を丸ごと差し替えず、`partials/<領域>.html` として置き、
  `mock.md` にどの領域を差し替えたかを書く（画面全体の正は既存の `index.html` のまま）。

### 上流との関係

モックは **design レイヤーの成果物**。モックを作る過程で**振る舞い（WHAT）の誤り**に気づいたら、モックの中で
辻褄を合わせず `/pj:change` に投げて spec に戻す（concepts §4・§9）。モックが spec を鍛えるのは正常な経路。
